# Reply to PR findings after batch disposition

This cycle-level step has no assigned job. Use the current-plan handoff and then the canonical current-batch handoff only when no scheduler batch assignment exists. Follow `$CODEINFO_ROOT/codeinfo_markdown/shared/review-artifact-handoff.md`. Derive the exact immutable batch and read all jobs/common findings, gate removals, combined filtering audit, disposition, research/normal/stronger repair records, outcome, current target heads, and any directly referenced prior reply assessment/task/job evidence for this same operation. Carry relevant direct references into this assessment and, when needed, the next applicable snapshot's `pr_preparation.evidence`. Do not search sibling batches, create new pointers, or infer history from a current pointer. Write a self-describing reply and candidate assessment in that batch's existing `reconciliation/` area; do not modify original outputs.

Process each actual remote finding across inline comments/thread replies, review bodies, and issue/conversation comments. Before deduplication or filtering, enumerate every actual potential-issue source ID across all three channels; conserve source IDs, author, URL, head, channel, and mappings through accepted, rejected, duplicate, and late dispositions. Status, refusal, quota, and other control messages are not findings. Re-read live PR feedback read-only for late comments. A single failed or denied repository-provided source/access mechanism makes that route unavailable for this operation; do not retry it during later polling, batches, administrative-head review, or cycle re-entry. A separately documented available alternative may be tried once. Preserve accessible channels and reviewer outcomes; unavailable evidence is not a clean pass. Reuse applicable assessment and direct evidence within this operation's existing conversation and execution ancestry, without creating new root IDs or ledgers. An explicitly fresh user operation may start fresh only after reconciling exact-head launches. For every newly arrived potential-issue source, determine disposition even if it may ultimately be rejected or duplicate. Reuse an existing authoritative disposition only when its source mapping proves applicability. Otherwise route exactly one same-head, gates-only pass to establish disposition, reusing the existing launch without pushing, refreshing the description, or requesting another review. Failed or ambiguous reply publication must be recorded against its source without unbounded retries or another review request.

Reply to each actual finding with `Accepted` or `Rejected` and a concrete rationale grounded in the authoritative gate/disposition. For optional attribution of already-authorized messages, follow the AI message attribution subsection in `$CODEINFO_ROOT/codeinfo_markdown/codeinfo2_implement_story/shared.md`. Filtered removals must say rejected and give the exact scope, authorization, or materiality reason; never resurrect them. For accepted repaired findings, cite exact repair commit(s) and focused proof actually run, including limits. Accepted unresolved findings remain pending/unrepairable with their existing settlement task owner when one exists; never invent a task. Do not claim a fix without committed code and proof. Use supported inline thread replies for inline findings. For review-body or issue-comment findings, use supported conversation replies that quote or link the origin ID; do not use an inline-only endpoint.

Posting is narrowly authorized for scoped PR replies. Use target-specific `.env.local` `CODEINFO_PR_TOKEN` parsed as data, provided only as child `GH_TOKEN`; never print/evaluate/save/export it, interpolate into arguments, or place it in a remote URL. First use installed GitHub CLI when safely available; otherwise use a discovered installed skill/tool with supported remote API instructions. Verify the exact host, repository, identity, and permissions. Never guess. If unavailable, preserve the missing reply as unavailable and continue other safe targets.

Make replies idempotent with existing markers keyed by source identity, disposition, and repair candidate, not batch. Inspect live replies before posting. Reuse an identical existing reply; a new meaningful proof/fix may update the agent's own reply or append one correction while preserving audit history. After posting, read back and verify reply ID, body, and parent/source relation. Before any repeat after ambiguous publication, reconcile live replies; reuse a matching reply and never duplicate it. A missing, failed, or ambiguous reply must be explicitly recorded against its source ID and disposition, without infinite retries or another review request.

Assess each target's exact remote launched/reviewed head, later candidate heads, outstanding actual findings and source-ID-level reply coverage, changed fix-bearing HEAD needing a new review, unavailable channels, and late candidates. Missing reply, source-ID mapping, or inaccessible-channel coverage remains explicit and is not cleanliness. Keep later administrative/checkpoint/documentation HEADs distinct from the exact head reviewers actually reviewed; never claim a newer head was reviewed. Preserve per-provider refusal/quota/failure and comparison limitations alongside usable sibling findings in the existing batch outcome/settlement, without requiring every provider to succeed or forcing the whole cycle incomplete solely for a terminal provider decline. A newly arrived finding may use an existing authoritative disposition only when applicability is proven; otherwise use one same-head gates-only pass reusing the launch, with no push, description refresh, or new reviewer request. Repeat only justified useful actions. Never request a new review for an unchanged candidate or retry unchanged quota/refusal/failure.
