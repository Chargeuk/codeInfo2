# Commit the documented story and attempt a push

Apply the shared documentation evidence contract to every content edit and consistency check: inspect relevant branch-authored README/docs, design and architecture notes, changelogs, and relevant archived original story files alongside code, comments, commit messages, and tests. Include story-owned staged, unstaged, and untracked docs as appropriate; verify current claims against implementation and actual diff, attribute documented rationale, and label superseded approaches as historical. Unsupported proposals or conflicting claims are evidence limits, never extra tasks, blockers, review findings, or proof of test passes. Process all `retrospective_archive.entries` independently, preserve every verified mapping in any handoff update, and exclude administrative archive changes from delivered implementation.

Read `$CODEINFO_ROOT/codeinfo_markdown/retrospective_story/shared.md` and the exact current-plan handoff. Recheck the current branch, supported comparison base and initial HEAD, plan status, and `git status --short`. Repair any remaining plan-only contradiction, remove any `- **BLOCKER**` line or speculative review finding from Implementation notes, and keep only factual provenance limits in relevant story sections and task notes. Do not perform code review while preparing the story commit. If story-owned implementation remains uncommitted, name its paths and local-only status in the plan; do not claim it is in a commit or on the remote. Stage only the selected new plan, verified original-story archive paths described below, and any explicitly created companion story document; leave unrelated files untouched. Inspect `git diff --cached --name-status`, `git diff --cached --check`, and the staged story content. If unrelated files are already staged, preserve them and use `git commit --only -- <story paths>` so the story commit excludes them. If a safe story-only commit is unavailable, report that limitation and continue to the final reingest rather than committing unrelated work.

Recover `retrospective_archive.entries` from the current-plan handoff. Verify each mapping independently against repository evidence under the shared contract, including the allocated base or positive integer suffix destination and content hash. Include ALL verified archive destinations and relevant source deletions in this plan-only commit, alongside the selected new plan; do not assume a single source or destination. Retain earlier verified pending mappings when a source was archived repeatedly. Build one deduplicated explicit path list: for each verified mapping include its allocated archive destination; include its source only if it is tracked and still deleted, or is now the selected new plan at a reused path; an absent untracked source is not a Git pathspec. If a different file now occupies an old source path, leave it untouched and report the evidence limit. A failed source deletion is not a completed move: preserve its per-file accounting, include any independently verified created archive, and do not stage the still-present source unless it is the selected new plan.

Stage these verified paths with `git add -A -- <story paths>`, including tracked deletions; never use a directory-wide add. Preserve unrelated staged files and use `git commit --only -- <story paths>` when needed. Inspect the staged diff and verify every archive's bytes against its recorded hash, including original dirty or untracked content. A reused source path is added only once as the new plan; do not attempt a separate `git rm` on it. Missing or conflicting evidence for one mapping means omit only that unsafe mapping and report the limitation; continue with all other verified mappings, not guessed files. The ignored archive receipt must remain uncommitted.

Commit the story files with the repository's required `DEV-[Number] -` subject and a four- or five-sentence body explaining the retrospective plan, preserved original stories when archived, documented implementation, open final validation task, and any material evidence limit. Verify the commit contains only intended story files and record the commit SHA. After a successful story commit, attempt `git push -u origin HEAD` for the current branch. A commit or push failure is nonfatal for this documentation flow: report the exact failure succinctly and finish this step successfully so the final reingest still runs. Do not amend, force-push, retry with changed credentials, or stage unrelated work merely to make the push pass.
