# Retrospective story contract

This flow documents implementation that already exists. It is not a code review or a test-adequacy review. Every agent step is documentation-only: read Git, source, branch-authored documentation, comments, commit messages, existing test files, logs, and read-only status helpers; edit only the new story plan and its handoff, apart from the explicitly requested first-step archive and ignored receipt, branch creation, branch pushes, plan-only commit, and verified superseded current-task/live-review-control preservation or invalidation under the lifecycle rules below. Never build, execute tests, run lint or formatting tools, start services, perform manual testing, capture screenshots, or modify implementation or test code. The native reingest steps are part of the flow and may run as configured. Read the target repository's `AGENTS.md` and `codeinfo_markdown/repository_information.md` when present. Use `code_info` first for repository facts, then inspect Git and source files directly. Treat indexed content as navigation help; Git and current disk contents establish the actual work.

The first step archives every verified top-level numbered story matching the fresh current branch's numeric story ID, in deterministic filename order before working reingest. Several matching files are confirmed scope, not ambiguity. Discover current sources afresh on every invocation; a prior receipt never suppresses a present replacement source. Allocate `planning/one-shot/one-shot-<original-stem>.md`, then `-1.md`, `-2.md`, and so on before the extension using exclusive creation; occupied names and allocation races advance the suffix rather than skip the source. Existing archives remain untouched. No matching source is a normal no-op; unknown branch identities and unsafe paths are safe no-ops. Per-file errors are nonfatal and do not stop remaining verified sources or the flow.

Recover outcomes independently from the ignored `codeInfoStatus/flow-state/retrospective-archive.json` receipt and repository evidence, never a previous agent report. The receipt's `entries` list contains each source path, allocated archive path, content hash, status, and reason. Independently verify every mapping: a top-level numbered source matching the recorded branch's numeric ID, a regular archive file under `planning/one-shot/`, the exact `one-shot-<original-stem>.md` or positive integer suffix relationship, and bytes matching `content_sha256`. A present source does not invalidate an earlier mapping: it may be a replacement that must also be archived. This preserves evidence of original dirty or untracked content after source-path reuse. Keep all verified prior mappings alongside fresh outcomes, including earlier pending archives when HEAD advanced on the same numeric story; a no-source repeat recovers them without moving archives. If a move created a verified archive but failed to delete its source, retain that mapping and its error honestly; retry the still-present source on the next invocation.

Before layout copies the receipt, verify its fresh branch and initial HEAD against Git and validate its entries independently. Copy it as `retrospective_archive` in the new current-plan handoff; preserve it through branch publication, renumbering, and every later handoff update. Later agents process all `retrospective_archive.entries` independently and retain every verified archive mapping even if layout selected a different branch number. Missing, malformed, stale, conflicting, or unverifiable entries are factual evidence limitations: salvage verified mappings, inspect Git and archive paths for trustworthy facts, omit unsafe staging, and continue safe plan work. Do not guess destinations from a base filename or assume only one archive. Never repoint the active handoff to a one-shot filename, which lacks the required numbered-plan prefix. Number allocation continues to scan only top-level `planning/*.md`; archiving all matching plans frees the number unless another top-level plan or same-namespace branch collides.

Exclude generated new plans, all verified archive destinations, and each administrative source deletion from delivered implementation inventory and base-to-HEAD or dirty-work comparisons. Do not let the archive alter the supported comparison base or manufacture delivered behavior. If the new plan reuses an old source path, that path is the new administrative plan, not additional implementation. Read relevant archived original story files as contextual documentation and compare their claims against actual implementation; archive relocation itself is never a completed implementation task. The final plan-only commit includes every independently verified archive destination, relevant tracked source deletions when still deleted, and the selected new plan, deduplicating repeated or reused paths. Per-file errors remain visible; an undeleted source is never represented as a successful deletion. The ignored receipt is never committed.

Throughout layout, section writing, tasking, checking, repair, audit, and commit preparation, inspect relevant branch-authored documentation alongside code, comments, commit messages, and tests: README files, docs, design and architecture notes, changelogs, and the archived original story where relevant. Inspect committed diffs and story-owned staged, unstaged, and untracked documentation as appropriate. Current behavior claims must agree with current implementation and the actual diff. Use relevant earlier commits and code for historical evolution; clearly label abandoned or superseded approaches as historical, never current delivered behavior. Attribute documented rationale to its documentation and verify consistency with code; code does not prove motivation. Authored documentation and tests do not prove execution or test passes. Documentation/code disagreements are factual evidence limits, not blockers or code-review findings. All content edits follow this documentation evidence contract.

For every verified archived original plan, independently account for every source section and material item in the replacement plan using a compact source-section/item → destination-section map inside existing plan sections; add no schema, report artifact, or plan section. Summarize faithfully without losing material information: overview, explicit requirements and acceptance criteria, exclusions, decisions and rationale, examples, dependencies, completed work and remaining required work, test evidence and limitations, superseded or future material, and meaningful Questions content (facts, unresolved questions, and answers/status) relocated into existing sections without creating a Questions heading. Classify each item as implemented only when current Git/source evidence demonstrates it; still-required explicit requirement, preserved honestly in the scope contract without claiming it passed; superseded, with an evidence-based reason; or future/excluded proposal, retaining its original status and reason. Do not drop an incomplete explicit requirement because implementation lacks it, and do not implement missing code or convert assumptions into repair tasks. Original exclusions remain exclusions. Distinguish explicit requirements from speculative suggestions in Description, Acceptance Criteria, Out Of Scope, Implementation Ideas, and tasking, so later prompts do not delete requirements under blanket “future proposal” rules. A section-heading-only inventory is insufficient when it drops item detail. Preserve faithful summaries or exact material details where needed; never invent passes, authorization, outcomes, or rationale. The final proof task remains open. Process every archive entry independently and continue after per-entry limitations. Generic instructions to remove future material, use only observed diffs, or exclude unsupported claims apply to speculative suggestions and unverified claims; they do not erase explicit original requirements.

Create every replacement branch from the currently checked-out `HEAD`, preserving the implementation; never checkout or fork from `develop`. In layout, set current-plan `branched_from` to literal `develop` for both new and reused branches as a policy marker, while preserving actual original source branch and starting SHA in the plan and `initial_head_commit`. Fetch `origin` and resolve freshly fetched `origin/develop`; store its verified SHA as `comparison_base_commit`, or null with the fetch/ref uncertainty. Never substitute a local fallback or claim remote verification. Keep source attribution and implementation merge-base range separate from this remote comparison-base tip. For the story delta, calculate `git merge-base <verified-origin-develop-sha> <initial-head>` and compare that merge-base to initial HEAD (`git diff <merge-base> <initial-head>` or equivalent three-dot range). Never use `git diff <develop-tip> <initial-head>` as the story delta because divergent develop commits would appear as story deletions. If merge-base is unavailable, record a null/unavailable delta range and salvage history/source evidence without guessing. The actual original feature parent may inform historical attribution only; it is never the review base. At layout and final audit/closeout, use fresh refs to check the existing resolver’s actual selection rules for this target without running a review. If fresh `origin/HEAD` is `develop`, it selects `origin/develop`; a nondefault `develop` may also be selected when it is the unmerged parent and HEAD descends from it, otherwise the resolver falls back to its selected default branch. Report an actual limitation only when those rules cannot select develop for this target. Do not modify or invoke the review engine. Preserve retrospective fields, archive receipts, and additional-repository evidence in every handoff rewrite; do not use a generic refresh that strips them.

Early publication and final publication each have at most three bounded collision-reconciliation/publication attempts, including live checks immediately before push and after push. Fetch/ref resolution is performed once per required refresh; do not add unbounded fetch retries. On numeric collision rerun `python3 "$CODEINFO_ROOT/scripts/select_retrospective_story_number.py" --owned-plan <current-plan-path>` at repository root. A published branch stays untouched; create replacement branches from current `HEAD`. Rename only a safe unpublished branch proven flow-owned. Move only the flow-owned new plan and repair its internal references and `current-plan.json`. Never invoke `select_current_task.py` or promote a task in this documentation-only flow. That helper changes the earliest TODO task to `__in_progress__`, while its checker expects one active task; both conflict with the required open final `__to_do__` task and unchecked boxes. Preserve the final task status and checkboxes. At layout or after final renumbering, invalidate only a `current-task.json` verified to belong to the superseded selection; preserve its bytes safely where ownership and an established archive location permit, then clear the obsolete live reference. If identity/ownership is uncertain, leave it untouched and report the limitation. Do not create a replacement handoff or synthesize selector payloads. A missing current-task handoff is expected and reported as `not selected/documentation only`; an existing unverified handoff is not claimed valid/resolved. Read-only `plan_status.py` or `check_current_task_handoff.py` may diagnose state; missing/non-resolved status is not a flow failure. The later normal implementation flow may select a task with the unchanged helper. Do not call `initializeReviewCycle`; it starts a review. The four live scratch controls are `codeInfoStatus/flow-state/active-review-cycle.json`, `review-disposition-state.json`, `minor-review-fix-result.json`, and `review-initialization-failure.json`. Inspect their stored identity and context. Only when a control is verified as superseded by the prior selection may it be archived byte-for-byte under the existing `codeInfoStatus/flow-state/review-cycles/<verified-cycle-id>/` using a non-overwriting destination; if that destination exists, verify identical bytes before treating preservation as complete, and never overwrite different history. Clear its live path only after preservation is verified. Never overwrite different history, copy an unowned/uncertain control, or alter immutable historical cycle artifacts. If the plan path is reused, compare control identity with original branch/HEAD context before treating it as current. If ownership or cycle identity is uncertain, leave state untouched and report the limitation. Do not create/run a review. Never remove or rewrite the retrospective archive receipt. Preserve unrelated state, refs, and files. No force-push, amend, competitor deletion, or credential changes. Exact same-branch remote presence is not numeric collision and push does not atomically reserve a number. Log each old → new identity, reason, and outcome. Retry ordinary transient failures only within this bound; report partial publication honestly and reuse valid corrected identity on rerun.

At final close-out stage only the selected plan, independently verified archive paths, applicable already-tracked story handoff controls, and a tracked deletion of the prior flow-owned plan path after final renumbering. Record old → new plan paths in existing plan/state evidence. Include the old path only when it is tracked and verified deleted; never pass an absent untracked old path as a pathspec. A replacement plan destination must be verified unoccupied before moving; never overwrite. A tracked superseded current-task or live-control deletion is allowed only with the same verified ownership and preservation rules above. Never promote a task during renumbering or claim that current-task is selected/resolved; preserve the final task as `__to_do__` with all checks open. Never force-add ignored controls or receipts. Verify staged paths exclude unrelated work and immutable historical artifacts. After push verify `git ls-remote --heads origin refs/heads/<branch>` returns that exact full ref with a SHA equal to local `HEAD`; absent, failed, or mismatched verification is not success. At final audit/closeout, fetch origin once and resolve the latest `origin/develop`; update the recorded comparison-base SHA or its explicit limitation while preserving original `initial_head_commit`. Do not reattribute flow-plan commits as implementation. If final renumbering occurs, update plan refs and handoffs and commit the story-only change, including any verified tracked deletion of the old flow-owned plan path, before push verification. Flow output reports branch, plan, remote base, identity changes, commit, push status, and limitations without confirmation stalls.

The initial layout creates the plan and applies the remote-base and replacement rules below. It records the previous handoff path before replacing it. The immediately following publication step rereads the handoff and uses the bounded collision procedure below; push failure is an evidence limitation, not a flow stop. Every later step reads `current-plan.json` for exact plan path, comparison base (including null), initial HEAD, `branched_from`, archive receipt, and repository scope, and verifies the active plan identity before editing. At final audit and closeout refresh origin/develop once, update only comparison-base evidence, and preserve initial HEAD. Separate flow plan commits from historical implementation commits. Keep the remote review base separate from any source-attribution or merge-base implementation range. Inspect staged, unstaged, and untracked work and exclude generated plan and administrative archive changes from implementation evidence. If remote base evidence is unavailable, preserve null and state why; do not invent a fallback. If HEAD or source drifts, refresh evidence and explain the snapshot. If plan identity cannot be verified, make plan edits a safe no-op and report the limitation.

Inspect dirty work to identify its relationship to the story. Document story-owned staged, unstaged, or untracked implementation as local-only evidence with exact paths and an explicit warning that a plan-only push will not publish those changes. A task may describe implemented work on disk, but must not claim an implementation commit or remote availability without proof. Keep unrelated dirty files untouched. Do not let imperfect evidence prevent tasking, audit, or a safe plan-only commit attempt; preserve material limitations in the relevant existing story section and `#### Implementation notes`.

Read only the bounded sections of a large plan using `$CODEINFO_ROOT/scripts/plan_sections.py` or focused `rg` and `sed` reads. Do not write secrets or machine-specific paths outside the plan's `Additional Repositories` entries. Keep the plan's scope tied to observed branch changes and verified archive accounting; do not invent intent, outcomes, test passes, or commits. Preserve still-required explicit requirements in the scope contract, without claiming they are implemented or passed. Source changes prove implementation only, not test execution.

For each story-owned change, inspect the changed code and tests, newly added or modified comments in the diff and current source, and the subject and body of relevant implementation commits. Use bounded Git history: list candidate commit SHAs and subjects first, then read the bodies of relevant commits and their diffs. Comments and commit messages can explain intended behavior, motivation, and task boundaries, but are claims to verify against current code, tests, and the actual diff. When they disagree, document the discrepancy rather than repeating stale intent as delivered behavior. Do not treat a commit message, a comment, or an authored test as proof that a test ran or passed.

This plan is a retrospective record and does not authorize new implementation. Its top-level `### Description`, `### Acceptance Criteria`, and `### Out Of Scope` are the scope contract. Preserve and classify every explicit archived requirement there under the archive-accounting rule; requirements state what must be validated, not that they passed. Later reviewers verify observed branch behavior, preserved explicit requirements, appropriate automated test coverage, the three standing code-quality criteria, and story-caused defects or regressions. This flow does not perform that review. Do not add requirements beyond observed implementation or preserved explicit archive requirements; requirements categorized as future/excluded or superseded do not authorize current delivery. Reviewers must not turn nearby issues, TODOs, template examples, preferred designs, or uncertain evidence into new requirements; original exclusions remain excluded. Do not create a Questions heading; preserve material facts, unresolved questions, and answers/status from archived Questions in the appropriate existing sections. Put material limits on identifying or attributing implemented work in the relevant existing story section or task Implementation notes. State acceptance requirements without judging whether current code or tests satisfy them. Do not add `- **BLOCKER**` lines, suspected missing-work lists, or code-review findings to any Implementation notes. A read-only status helper may report open work; that status is not an instruction to add blocker notes. Do not turn perceived code or test gaps into new tasks or final-task work. Evidence limits are not future implementation requests. A scope expansion needs an explicit user instruction and an updated story contract.

The templates are layout references only: exclude prospective planning instructions, a Questions heading/placeholder, and generic implementation-blocker guidance from this retrospective story. Before omitting a Questions heading, preserve material archived facts, unresolved questions, and answers/status in existing sections. This flow's explicit no-blocker rule overrides blocker advice in `plan_format.md` and the shared final-task contract. The planning template lookup is: current working repository's `planning/plan_format_no_tasks.md`, then `codeInfo2` through `code_info`, then another indexed repository. The task template follows the same order for `planning/plan_format.md`. If no template can be found, use the headings established by the current repository's existing plans and report the fallback.

The final task is deliberately open. Follow `$CODEINFO_ROOT/codeinfo_markdown/shared/final-task-creation.md` for its shape and repository-supported commands. Document its future build, suite, lint, formatting, and manual checks without executing or checking them off in this flow. Earlier implementation tasks may be `__done__` when their work is demonstrated by Git and source evidence. Mark an earlier testing checkbox complete only with evidence of that exact test execution; otherwise leave historical test execution unstated or explicitly unverified and rely on the open final task for future full validation. The final task starts open with unchecked checks and no blocker lines in Implementation notes.
