# Retrospective story contract

This flow documents implementation that already exists. Read the target repository's `AGENTS.md` and `codeinfo_markdown/repository_information.md` when present. Use `code_info` first for repository facts, then inspect Git and source files directly. Treat indexed content as navigation help; Git and current disk contents establish the actual work.

The initial layout step creates this flow's plan and replaces any older current-plan handoff; it must discover branch evidence independently. On every later step, read `codeInfoStatus/flow-state/current-plan.json` to identify the exact `plan_path`, `comparison_base_commit` when established, `initial_head_commit`, and additional repository scope. Confirm the handoff points to an existing retrospective plan for the current branch before editing it; an old or unverified handoff is not authority to edit another story. Reopen the selected plan from disk and recover needed facts from the plan, Git, source, and repository instructions rather than a prior agent's conversation or step report. Do not select another plan or invent a missing comparison base. Compare a supported base to the initial HEAD and separately inspect staged, unstaged, and untracked work; exclude the newly generated plan from implementation evidence. If the base is ambiguous or unavailable, preserve `comparison_base_commit: null`, document the candidate ranges and their differences under `### Questions`, and use only changes directly supported by Git and current source. If HEAD or relevant source changes drift during the flow, refresh the evidence and explain the changed snapshot in the plan. Continue with the best supported story; when the plan identity cannot be verified, make plan edits a safe no-op and report the limitation.

Inspect dirty work to identify its relationship to the story. Document story-owned staged, unstaged, or untracked implementation as local-only evidence with exact paths and an explicit warning that a plan-only push will not publish those changes. A task may describe implemented work on disk, but must not claim an implementation commit or remote availability without proof. Keep unrelated dirty files untouched. Do not let an unanswered question or imperfect evidence prevent tasking, audit, or a safe plan-only commit attempt; preserve the limitation in `### Questions` and relevant `#### Implementation notes`.

Read only the bounded sections of a large plan using `$CODEINFO_ROOT/scripts/plan_sections.py` or focused `rg` and `sed` reads. Do not write secrets or machine-specific paths outside the plan's `Additional Repositories` entries. Keep the plan's user-facing scope tied to observed branch changes and explicit user instructions; do not invent intent, outcomes, test passes, or commits. A source change is evidence of implementation, not evidence that an automated or manual test passed.

This plan is a retrospective record, not authorization for additional product work. Its top-level `### Description`, `### Acceptance Criteria`, and `### Out Of Scope` are the scope contract that later tasking and review agents read. State explicitly in those sections that reviewers should verify the observed branch behavior, the three user-required code-quality criteria, and story-caused defects or regressions; they must not turn nearby issues, TODOs, template examples, preferred designs, or uncertain evidence into new features or unrelated repair tasks. Put unsupported claims and missing proof in `### Questions` as evidence limitations, not future implementation requests. A scope expansion needs an explicit user instruction and an updated story contract.

The planning template lookup is: current working repository's `planning/plan_format_no_tasks.md`, then `codeInfo2` through `code_info`, then another indexed repository. The task template follows the same order for `planning/plan_format.md`. If no template can be found, use the headings established by the current repository's existing plans and report the fallback.

The final task is deliberately open. Follow `$CODEINFO_ROOT/codeinfo_markdown/shared/final-task-creation.md` for its shape and repository-supported commands. Do not run or check off its build, suite, lint, formatting, or manual guidance in this documentation flow. Earlier implementation tasks may be `__done__` when their work is demonstrated by Git and source evidence. Mark an earlier testing checkbox complete only with evidence of that exact test execution; otherwise put the missing full regression check in the open final task and explain the historical evidence limit in Implementation notes.
