# Research and repair recurring review findings

Read and follow `$CODEINFO_ROOT/codeinfo_markdown/shared/review-artifact-handoff.md` and `$CODEINFO_ROOT/codeinfo_markdown/shared/repeated-review-repair.md`. Work autonomously; never wait for human input. This invocation owns the current batch's possible repeats and unresolved history-matching uncertainty, not its ordinary new findings.

Read the exact immutable batch disposition, filtering evidence, target snapshot, bounded current story contract, and repeated-finding routing artifact. Recover missing routing from current disposition and the read-only history helper before implementing anything. Expand each relevant historical reference with `python3 "$CODEINFO_ROOT/scripts/review_findings.py" expand --reference '<reference>'` from the target repository. If a reference is stale, rerun the list with the current batch excluded and re-establish the historical identity; never use a reused Finding ID alone. Related repair packets are batch-linked evidence, not a claim that every task fixed this particular finding.

For each candidate:

1. Determine whether the historical and current findings concern the same underlying behavior. A false match returns to ordinary repair with a reason. Merely lacking a historical description does not disprove a match.
2. Inspect full accepted records, relevant `Addresses Findings`, implementation notes, exact repair commits/diffs, later reversals, final-validation evidence, and current source/tests. Follow established historical artifact references for read-only evidence; keep writes in the current batch and its authorized target repositories. Record what changed, why the prior repair was reverted or incomplete, and any missing explanation. Do not invent a reversal rationale from the existence of a revert alone.
3. Independently confirm current positive authorization and materiality. Allowed authority is the current top-level Description, Acceptance Criteria, Out Of Scope, a user-approved expansion incorporated there, or comparison-base evidence of preserved behavior. Historical acceptance, tasks, commits, and tests are evidence only. Preserve all earlier gate removals; do not resurrect rejected findings or narrowed-away remedies. An authority conflict is not an actionable implementation task.
4. Plan and implement the smallest repair satisfying both the reported defect and the valid behavior the earlier correction or reversal protected. Avoid replaying the same unsuccessful fix. Research broadly when needed, but change only the direct cause and necessarily coupled files; no surrounding cleanup, speculative policy, dependencies, or unrelated refactoring.
5. Add or update proportionate focused proof for both sides of the conflict, run the repository-owned test wrappers, inspect failures, and revise using new evidence. A reverted regression test is evidence to understand, not automatically a correct test to restore. Continue while materially different evidence-backed approaches remain; do not repeat unchanged attempts. If requirements are irreconcilable, capabilities unavailable, approaches exhausted, or the invocation reaches its practical execution limit, preserve the exact unresolved limitation.

Before editing each target, confirm immutable-batch ownership, expected branch, current HEAD/worktree, and repository instructions. Preserve unrelated work. Process target repositories sequentially in dependency order and continue safe work when another target is unavailable. After repairs, use each changed repository's supported formatting and lint workflow, rerun affected proof after formatting changes, and create separate repair commits with its required story prefix. Do not push or create implementation tasks.

Append a self-describing research audit to the current batch's repeated-finding artifact, retaining the matcher's provenance. For every assigned candidate record: confirmed repeat or false match; historical identities; earlier fixes and reversal evidence; current authority; hypotheses/attempts; necessary files changed; initial/final HEADs; exact commits; tests, formatting, lint and results; and fixed, already resolved, returned to ordinary repair, gate conflict, or unresolved outcome. Uncertain/unavailable cases remain explicit. Explain why any genuinely different next repair approach would be useful; exhausted unchanged attempts must not keep the repeated review group running.

One research invocation is allowed per batch. Confirmed or uncertain repeats left unresolved must pass to existing complete-pass settlement, not back to normal/stronger repair for another blind attempt in this batch. Ordinary findings and disproved matches remain eligible for the existing repair path. Reopen the artifact before returning; missing proof or artifact coverage is never a successful fix. No global termination guarantee is implied by this bounded stage.
