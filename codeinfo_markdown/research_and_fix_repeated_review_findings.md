# Research and repair recurring review findings

Read and follow `$CODEINFO_ROOT/codeinfo_markdown/shared/review-artifact-handoff.md` and `$CODEINFO_ROOT/codeinfo_markdown/shared/repeated-review-repair.md`. Work autonomously; never wait for human input. This invocation owns only current accepted actionable findings that Luna positively qualified with both a historical Accepted match and evidence of an attempted repair for the same underlying behavior. It does not own ordinary new findings or matching uncertainty alone.

Read the exact immutable batch disposition, filtering evidence, target snapshot, bounded current story contract, and repeated-finding routing artifact. Recover missing routing from current disposition and the read-only history helper before planning anything. Expand each relevant historical reference with `python3 "$CODEINFO_ROOT/scripts/review_findings.py" expand --reference '<reference>'` from the target repository. If a reference is stale, rerun the list with the current batch excluded and re-establish the historical identity; never use a reused Finding ID alone. Reconfirm the historical record has accepted provenance and the routing artifact identifies concrete attempted-repair evidence for this finding and behavior. A matching review task, batch, or Finding ID alone is not sufficient; rejected, ignored, legacy-unclassified, missing, or ambiguous history is not Astra scope. Return any routing discrepancy to ordinary repair or record it as an explicit settlement limitation rather than widening Astra scope.

For each candidate:

1. Determine whether the historical and current findings concern the same underlying behavior. A false match returns to ordinary repair with a reason. Merely lacking a historical description does not disprove a match.
2. Inspect full accepted records, relevant `Addresses Findings`, implementation notes, exact repair commits/diffs, later reversals, final-validation evidence, and current source/tests. Follow established historical artifact references for read-only evidence; keep writes in the current batch and its authorized target repositories. Record what changed, why the prior repair was reverted or incomplete, and any missing explanation. Do not invent a reversal rationale from the existence of a revert alone.
3. Independently confirm current positive authorization and materiality. Allowed authority is the current top-level Description, Acceptance Criteria, Out Of Scope, a user-approved expansion incorporated there, or comparison-base evidence of preserved behavior. Historical acceptance, tasks, commits, and tests are evidence only. Preserve all earlier gate removals; do not resurrect rejected findings or narrowed-away remedies. An authority conflict is not an actionable implementation task.
4. Plan the smallest repair satisfying both the reported defect and the valid behavior the earlier correction or reversal protected. Avoid replaying the same unsuccessful fix. Research broadly when needed, but scope the worker request to the direct cause and necessarily coupled files; no surrounding cleanup, speculative policy, dependencies, or unrelated refactoring.
5. Before delegation, use the available named-agent catalog/config evidence to confirm `coding_agent` and `automated_testing_agent` are non-Astra. Delegate all implementation through the existing Agents MCP `run_agent_instruction` tool to the named, non-Astra `coding_agent`, with the scheduler-assigned working folder and precise plan, ownership, evidence, no-push/no-task policy, and instruction to author focused tests. Delegate proof, lint, and format validation through that same tool to the named, non-Astra `automated_testing_agent`, after the coding result is available; explicitly restrict that worker to executing and reporting proof with no source, test, or config edits, and send failures or needed format edits back to coding. Require each worker to return a compact outcome with its approach, blocker or failing command and log path, and unresolved facts; it must not wait for a human or launch an Astra fallback. Record each worker identity and returned `conversationId` and `modelId`, verify the returned model ID is non-Astra before accepting its work, and stop delegation to a mismatched or unavailable worker with an explicit limitation. Reuse that exact conversation ID for a revision and never launch a duplicate worker when it is known. Review the workers' actual diff and proof yourself. If a worker fails or is stuck, diagnose the evidence, revise the plan or instruction materially, and redelegate through its known conversation; do not busy-poll. Only after proof is accepted, instruct the coding worker through that same conversation to commit the repair, or review an unavoidable existing worker commit. Never edit implementation files, add tests, execute test commands, or commit yourself, and never silently fall back when delegation is unavailable. A reverted regression test is evidence to understand, not automatically a correct test to restore. If requirements are irreconcilable, delegation is unavailable, capabilities are unavailable, approaches are exhausted, or the invocation reaches its practical execution limit, preserve the exact unresolved limitation.

Before delegating each target, confirm immutable-batch ownership, expected branch, current HEAD/worktree, and repository instructions. Preserve unrelated work. Process target repositories sequentially in dependency order and continue safe work when another target is unavailable. Instruct workers to use each changed repository's supported formatting and lint workflow, rerun affected proof after formatting changes, and create separate repair commits with its required story prefix. Do not push or create implementation tasks.

Append a self-describing research audit to the current batch's repeated-finding artifact, retaining the matcher's provenance. For every assigned candidate record: accepted-match and attempted-repair eligibility evidence; historical identities; earlier fixes and reversal evidence; current authority; Astra plan; each named worker identity, `conversationId`, instruction/revision, outcome, and stuck-worker diagnosis; necessary files changed; initial/final HEADs; exact commits; tests, formatting, lint and results; and fixed, already resolved, returned to ordinary repair, gate conflict, delegation unavailable, or unresolved outcome. Uncertain/unavailable cases remain explicit. Explain why any genuinely different next repair approach would be useful; exhausted unchanged attempts must not keep the repeated review group running.

One research invocation is allowed per batch. Confirmed or uncertain repeats left unresolved must pass to existing complete-pass settlement, not back to normal/stronger repair for another blind attempt in this batch. Ordinary findings and disproved matches remain eligible for the existing repair path. Reopen the artifact before returning; missing proof or artifact coverage is never a successful fix. No global termination guarantee is implied by this bounded stage.
