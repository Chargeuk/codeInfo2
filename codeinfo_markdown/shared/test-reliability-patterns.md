# Test reliability patterns

Use this reference when the story/user contract authorizes repairing brittle tests or test-harness code that prevents required validation. That authority can include tests unrelated to or predating the story; it does not authorize unrelated production behavior changes. A failed check is evidence to investigate, not proof of brittleness. Establish the failing seam and intended correctness contract before repairing it; a product bug still needs its own implementation authority.

These examples are nonexhaustive guidance, not an all-story checklist or a requirement to add helpers, dependencies or infrastructure. Prefer existing repository helpers and the smallest evidenced repair.

- **Fixed sleeps:** replace arbitrary pauses with an observable event or state boundary and an existing bounded wait with useful failure context. Deliberate mock pacing or timeout simulation is different from waiting for correctness by elapsed time.
- **Event ordering:** arm an event, response, abort or completion waiter BEFORE the trigger, trigger the operation, then await that waiter. Otherwise fast results can arrive before the observer exists.
- **Operation completion:** await the prior operation's actual completion before starting dependent work. Dispatch accepted does not mean finished; a loading indicator or accepted request alone may precede the result the next action needs.
- **Controls and selection:** wait for an actionable control and its relevant transition, use scoped selectors that identify the intended owner, and obtain current locators after rerenders/replacement. A matching element can still be disabled, obscured or stale.
- **Eventual data and negative assertions:** wait for the expected observable data rather than assuming immediate propagation. Prove absence at a deterministic gate where the unwanted action could have occurred; an arbitrary delay followed by a negative assertion is not a reliable boundary.
- **Ordering and setup:** make each test establish its own prerequisites and data; do not depend on a previous test's side effects or execution order. Keep deliberate multi-step scenarios owned by one test or an explicit supported fixture lifecycle.
- **External resources:** use unique test-owned identities and supported ephemeral resources for ports, directories, databases, collections and runtime projects; avoid collisions with parallel tests or live development owners.
- **Cleanup and cancellation:** await cleanup of sockets, servers, timers, subscriptions, child processes and detached promises. Restore listeners, mocks, globals and environment overrides through existing scoped hooks, including on failure. Handle already-aborted signals, register one-shot abort listeners where appropriate, clean up other listeners and recheck across asynchronous registration boundaries.
- **Timeouts under load:** use repository-configured realistic bounds and meaningful readiness signals. Diagnose CPU saturation and resource ownership; do not blanket-increase timeouts or assume a short isolated timing budget is valid during parallel validation.
- **Inputs and environment:** make clocks, randomness, locale/timezone, seed data and external responses deterministic where they affect the assertion, using existing scoped controls. Restore the real environment afterwards and preserve the behavior the test is meant to exercise.

Preserve intended coverage and correctness checks. Do not remove assertions, skip failing proof, mask races with retries, or weaken required validation to obtain a pass. Test-repair authority alone does not permit changing production behavior, broad cleanup or new frameworks. The coder owns test/harness repairs and the tester owns execution under the calling workflow's role boundaries. Verify the repair with focused diagnosis and then complete the required affected/full proof through supported wrappers and existing bounded recovery; report actual outcomes and remaining uncertainty.
