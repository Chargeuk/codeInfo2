# Set the CodeInfo2 story

Set up the user's explicitly selected local story for later implementation by safely aligning the work branch and `codeInfoStatus/flow-state/current-plan.json` with its plan. The local plan is primary; Jira is optional context. The selected plan may use the raw four-section story layout from `codeinfo2_plan_story.md`; do not require implementation tasks. This command performs setup only. It does not implement the story, run product or story tests, create tasks or subtasks, open a pull request, or do other workflow maintenance.

The user's clear selection authorizes the setup actions described here, including branch and handoff changes and an owned setup commit/push when safe. Do not ask for redundant approval. Preserve all existing work and report partial outcomes accurately. Do not use a picker, stop-condition checklist, verification loop, numeric branch allocation, or executable-task eligibility test as a prerequisite.

## Find and resolve the selected story

Start from the supplied working folder. Identify the repository root using available local Git evidence, read its root `AGENTS.md`, and consult its documented planning guidance, available skills, and supported tools to find story files and any optional Jira integration. Do not assume a repository path, Jira project/site/account, credentials, or remote identity. Use `code_info` first for consequential local-repository questions when available, then verify relevant facts from local files and source. Missing guidance or a tool limits only the read or operation that depends on it.

Use a clear user-supplied plan path, filename, story title, or Jira key directly. Resolve relative plan paths from the selected working repository root; accept absolute paths and relative paths containing `../`, including paths resolving outside this repository, another repository, or through a symlink. Do not relocate, renumber, or reject a selected plan because of its location. Report actual read or save failures and continue useful setup and planning where possible. If the user has not selected a story, offer a concise set of relevant local plans and, when available, Jira stories. Do not derive a candidate from `current-plan.json` or silently choose another story. If the input could identify more than one story, ask one focused clarification and continue any safe independent discovery or setup preparation; do not select a different story by default.

Prefer the existing local plan, including its agreed content and progress, over a new Jira description. Use repository-supported Jira reading only when useful and available; Jira access, credentials, configuration, or a ticket are never prerequisites. A Jira description can inform a genuinely missing plan, but must not replace or silently rewrite an existing developed plan. Do not assume that Jira fields or local stories have a particular schema.

Read the exact selected plan from disk. Support a raw story with the four sections used by `codeinfo2_plan_story.md`—Overview, Acceptance criteria, Out of scope, and Best practices—without requiring implementation tasks or testing checklists. Do not impose a filename eligibility gate on selecting or developing a story. Preserve the selected plan's exact path, layout, identifiers, history, content, progress, and user overrides; never rename or renumber it to satisfy a consumer. Follow documented repository naming conventions for a new plan. Current CodeInfo2 consumer evidence shows that `scripts/flow_state_utils.py` requires a story number at the start of a plan filename when loading plan scope. If the selected path does not meet a downstream consumer's constraint, continue other safe authorized setup, report selection/save status separately from implementation readiness, and identify that constraint under **What went wrong**; do not add a numeric validation loop or claim the plan is consumer-ready. If a plan is genuinely missing and the user supplied a story or usable Jira description, create a local draft following the target repository's documented conventions; use a counter only when those conventions establish one. Do not invent scope, requirements, tasks, tests, or ticket facts. If no safe source or destination is available, leave the plan unwritten and show a clearly labeled proposed draft inline when useful.

## Prepare the work branch

Before any mutation, inspect the actual checkout branch/ref and HEAD, plus staged and unstaged state. Preserve unrelated edits, staging, and commits. Identify existing same-story branches among local branches and available verified origin refs, using the selected plan's exact path or content together with available history evidence; a matching branch name alone is insufficient. Origin access is optional and unavailable origin refs do not block local setup. Reuse a verified same-story branch even if its slug differs from current conventions, and preserve its provenance when proven. Do not repurpose an unrelated branch.

Switch to a verified same-story branch only when checkout preserves all local work. If a new branch is appropriate, create it from the captured current branch/ref and HEAD (or captured immutable commit when detached), following documented repository naming conventions. If none apply, use `feature/<selected-plan-filename-without-.md>` when valid; do not fabricate a Jira number, renumber a plan, or guess `main`/`develop`. Use a minimal valid alternate name for a real collision only when it remains clearly tied to this story and does not reuse unrelated work. Never overwrite a branch or disturb edits to make a switch possible. An uncertainty or conflict skips only the affected branch action; continue safe independent local work.

Ordinary Git inspection and ref checks inform only the mutation that relies on them; they are not global gates. Missing optional provenance does not prevent setup. Do not stash, reset, clean, delete, or rewrite history. If branch preparation is unsafe, preserve the current state, report the reason, and continue any plan or handoff work that can safely proceed without claiming the branch is ready.

## Save the plan selection

Read `codeInfoStatus/flow-state/current-plan.json` independently, if present. Use the existing CodeInfo2 schema as documented in `set_current_story_handoff.md` for orientation only. Write only this canonical workflow-state file; do not create other handoffs or state. Set `plan_path` to the exact selected plan path relative to the selected working repository root, retaining `../` when needed for an external plan. Set `branched_from` only when a new branch was created from a captured source or the original source provenance of a reused branch is proven. Omit unknown optional provenance rather than guessing. Set `additional_repositories` to `[]` unless the user explicitly authorized other repositories and their actual paths and relevance are known; represent included repositories as `{ "path": "…", "branched_from": "…" }`, omitting an unknown optional `branched_from`.

Preserve valid metadata already associated with this same story and any unrelated fields required by the current schema. Do not carry over values from another story. Recover trustworthy fields from a missing, malformed, or stale handoff where possible. If an optional fact cannot be recovered, omit it and report that limitation. If the actual schema requires a fact that cannot be established, skip only the dependent write. Do not require an existing handoff to select a plan: this command creates or updates it. Never point the handoff at a missing or unsaved plan or claim the selection is saved when it is not. Plan storage does not change the working repository, branch, implementation scope, or explicit additional-repository scope; do not infer an implementation repository from the plan folder.

If the plan, branch, or handoff cannot safely be changed, preserve existing files and report the actual state plus proposed unsaved values where useful. A failure to save one item does not cancel independent safe local work. Distinguish a selection recorded in the handoff from implementation readiness when the branch is unresolved or a known downstream consumer cannot load the selected plan.

Jira is optional: never wait for it before continuing local setup. Read the issue and its visible description, acceptance criteria, and relevant fields as needed, without changing or resending them. Keep private configuration and credentials out of output and files.

If the issue identity or comment method is unavailable, skip the comment and report why. Before retrying an uncertain comment, read back recent comments and check for the same result; never blindly duplicate it. A Jira read or comment failure does not block local work.

## Commit and publish setup

Do not stage an external plan in the selected working repository. Commit the selected working repository's owned setup artifacts normally. Publish an external plan only from its actual owning Git repository when that publication is separately authorized within verified scope; otherwise leave it saved locally and report it as not published, while continuing authorized working-repository publication. Plan storage alone does not authorize implementation or publication in its repository.

The main agent owns commits and publication. When an authorized setup plan or handoff change is ready, commit only the exact files owned by this setup, preserving unrelated staged entries and existing commits. Do not include another person's work. If the change cannot be safely isolated, leave it local and report why. Reuse of already-correct setup creates no branch, empty commit, duplicate push, or duplicate comment.

Publish only the exact verified story branch, when remote access is available and the local result is safe to publish. Do not publish another owner's or unrelated unpublished commits in the push range. If the intended setup cannot be isolated from such commits without rewriting history, skip only the push, keep the local setup, and report why. For a new remote ref verified absent, a create-only lease with an explicitly empty expected value may guard creation; it must reject the push if the ref exists. For any existing remote ref, use an ordinary non-force fast-forward push. Never rewrite an existing ref or publish unrelated refs or tags. If credentials, remote access, or fast-forward conditions are unavailable, retain local work and report that it was not published. A remote failure does not roll back completed local setup or block an independent Jira comment. Run only documented contributor checks that apply to this setup and are authorized by the user and repository workflow; user restrictions take precedence. Do not add tests or a publication gate merely because an optional integration is absent. Report excluded, failed, or unavailable proof honestly and never claim it passed; continue other safe operations.
