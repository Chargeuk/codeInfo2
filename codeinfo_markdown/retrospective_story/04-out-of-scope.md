# Verify Out Of Scope

Read `$CODEINFO_ROOT/codeinfo_markdown/retrospective_story/shared.md` and the selected plan's `### Out Of Scope`. Examine nearby unchanged behavior, the actual diff, changed comments, and relevant implementation commit subjects and bodies. Treat messages and comments as clues to intended boundaries, then verify that the boundary matches the delivered changes. For each delivered behavior or workflow named in Description and Acceptance Criteria, write a concrete conceptual boundary: what the branch changed and which tempting adjacent behavior, policy, or product outcome it did not change. Use story-specific behavior and user-visible contracts rather than only file paths, component names, or a generic "no new features" bullet. A reviewer must not infer authorization from a shared file, subsystem, keyword, or plausible design direction. State a clear reviewer rule: this story validates observed branch behavior, the three required code-quality criteria, and defects or regressions caused by that work; a proposed finding outside those bounds needs a separate story or explicit user-approved scope expansion. New user-facing behavior, unrelated pre-existing bugs, adjacent cleanup, speculative hardening, and work inferred only from template examples or TODOs are outside this story. Do not use this section to hide a changed file or contradict an acceptance criterion. If scope is genuinely uncertain, record the uncertainty as an evidence limitation rather than guessing. Check this section against Description and Acceptance Criteria so later review cannot read the plan as authorization for additional product work.
