# Establish the branch snapshot and create the initial story

Read `$CODEINFO_ROOT/codeinfo_markdown/retrospective_story/shared.md` first. The native reingest step has already run. Confirm the working repository and use fresh Git reads: `git status --short --branch`, `git branch --show-current`, `git log -1 --format=%H`, `git remote -v`, branch tracking/provenance, and relevant refs. Establish an explicit comparison base for work already done when evidence supports one. Prefer recorded branch provenance or a clearly supported merge base against the source branch. Never treat the branch's upstream tracking ref as the source branch merely because it is configured. If multiple plausible bases produce materially different diffs and repository evidence does not resolve them, record the candidates and uncertainty under `### Questions`, set `comparison_base_commit` to null, and document only changes supported without choosing a speculative base. Inspect `git diff --stat <base> <initial-head>` and `git diff --name-status <base> <initial-head>` when a base is supported; always inspect `git diff --cached`, `git diff`, and untracked file names. Exclude unrelated files by evidence, not a blanket filename guess. Identify any story-owned implementation still uncommitted and record its local-only status; do not stage or commit implementation files.

Read existing plan filenames and branch conventions to select a collision-free seven-digit story number. Reuse the branch's story number when it is unambiguous and available; otherwise choose the next available number. Follow the target repository's branch instructions, creating a matching feature branch from the current checkout if required without discarding changes. Do not switch to a branch that would overwrite local work. Read the no-tasks template using the lookup order in `$CODEINFO_ROOT/codeinfo_markdown/retrospective_story/shared.md` and create `planning/<number>-<slug>.md` with its full initial heading layout and concise factual starter content. Use changed code, relevant new comments, and implementation commit subjects and bodies as clues for the initial title and sections, verifying each claim against source and diff evidence. Replace the template's prospective instructions and examples with retrospective content, including its instruction to empty Questions before tasking. Initialize `### Questions` with `- No Further Questions` when no actual decision is pending, followed by unnumbered evidence-limitation bullets when needed; do not turn limitations into numbered planning questions. State in the top-level story sections that the plan records observed branch work and bounds later review to that work and story-caused defects. Keep the title user-facing and based on observed behavior. Do not add `# Tasks` yet.

Write `codeInfoStatus/flow-state/current-plan.json` with the exact relative `plan_path`, `comparison_base_commit` as a verified SHA or null, `initial_head_commit` as the observed SHA when available, and `additional_repositories: []`. Include `branched_from` only when this step actually creates the feature branch and its source is known. A prior current-plan handoff may identify another story: this new-story flow may replace that transient handoff after reporting the old path and creating the new plan. Never edit the old plan merely because it was previously selected. Ensure the handoff path is ignored or otherwise handled according to repository rules. Report the branch, supported base or uncertainty, initial HEAD, plan path, and evidence limitations. If a safety-critical identity cannot be established, make the affected mutation a safe no-op, report why, and continue any independent work that remains possible.
