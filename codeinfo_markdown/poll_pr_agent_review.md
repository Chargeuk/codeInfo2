# Poll the pinned PR reviewer roster

This is a runtime instruction for one `pr_reviewer` observation. Follow `review_job_workspace_contract.md` and `$CODEINFO_ROOT/codeinfo_markdown/shared/review-artifact-handoff.md`; use the prepended scheduler `review_job`/`review_batch` paths, read `job.md`, every assigned input, immutable `batch-launch.md`, and current work evidence. Do not rely on conversation memory. Keep writes inside assigned `work/`; do not write final findings here. Never select siblings or change Git, plan, implementation, or remote requests.

For every API/tool call, follow `prepare_pr_agent_review.md`'s secret-safe target-specific authentication procedure afresh; this flow step runs after the prepare step's child process environment has ended. Never rely on inherited/persisted tokens or conversation-only credential context. Polling is read-only: do not request reviews or otherwise mutate GitHub.

Refresh every requested reviewer for the exact candidate using supported APIs/tools and live PR evidence. Verify the full repository, PR, head branch, intended base branch, and pinned pushed HEAD. Record actual base SHA and immutable comparison-base SHA, and inspect whether the live diff still represents the pinned comparison; an ordinarily advanced base SHA alone does not invalidate the candidate. For each observation record source and snapshot time plus available author/login, review/comment/check ID and URL, timestamps, review commit/head, check run, and request correlation. Acknowledge provider and comparison evidence limits. Review requests alone, empty `reviewRequests`, an acknowledgement without a finished review, a bot comment without completion evidence, stale/dismissed review, generic check success, or unrelated human comment is not terminal success.

Maintain an explicit state per requested reviewer: `pending`, `running`, or `unknown` are nonterminal; terminal outcomes are `success`, explicit `refusal`, `quota`, or `failure`. A success is usable only when attributable to that requested reviewer and exact candidate/head. A terminal refusal, quota, or failure ends waiting for that reviewer only; preserve its unsuccessful/unavailable coverage and continue waiting for every other requested reviewer that is pending, running, or unknown. Never require every reviewer to succeed, and never make one provider's terminal outcome end sibling observation. Unknown remains waiting unless factual evidence establishes a sustained inability to observe that reviewer. Healthy pending/running work must not be relaunched. Never request again in this step. A transient query failure alone is not terminal; only actual unavailable preparation/authentication or sustained demonstrable API capability failure may end the affected observation, and must be recorded honestly with evidence and resume conditions. Continue observing other reviewers wherever possible.

The flow performs an immediate observation, then uses the flow's native 300-second wait before polling again. Continue waiting for all requested reviewers to reach a terminal outcome, whether successful or unsuccessful. Do not shell-sleep or busy-loop. Pending, running, and unknown remain nonterminal and keep observation waiting until their state changes or a factual inability to observe that reviewer is established. When observation of one reviewer becomes genuinely unavailable, preserve that limitation and continue waiting for siblings that remain observable; do not fabricate a terminal reviewer outcome or current clean coverage.

Reopen and update the existing assigned evidence with the fresh status snapshot and per-reviewer state. State exact candidate/head, all statuses, evidence paths, and limits; do not claim clean coverage on unknown or stale evidence.
