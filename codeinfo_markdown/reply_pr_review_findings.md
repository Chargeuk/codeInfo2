# Reply to PR findings after batch disposition

This cycle-level step has no assigned job. Use the current-plan handoff and then the canonical current-batch handoff only when no scheduler batch assignment exists. Follow `$CODEINFO_ROOT/codeinfo_markdown/shared/review-artifact-handoff.md`. Derive the exact immutable batch and read all jobs/common findings, gate removals, combined filtering audit, disposition, research/normal/stronger repair records, outcome, and current target heads. Do not search sibling batches. Write a self-describing reply and candidate assessment in that batch's existing `reconciliation/` area; do not create a pointer/framework or modify original outputs.

Process each actual remote finding across inline comments/thread replies, review bodies, and issue/conversation comments. Conserve source IDs, author, URL, head, channel, and deduplication mapping. Re-read live PR feedback read-only for late comments. If a newly actionable finding arrives after gates, do not self-disposition it or invent a reply rationale: mark it pending for the next useful same-head batch processing and reuse the existing launch without requesting again. Status comments and quota acknowledgements are not findings.

Reply to each actual finding with `Accepted` or `Rejected` and a concrete rationale grounded in the authoritative gate/disposition. Filtered removals must say rejected and give the exact scope, authorization, or materiality reason; never resurrect them. For accepted repaired findings, cite exact repair commit(s) and focused proof actually run, including limits. Accepted unresolved findings remain pending/unrepairable with their existing settlement task owner when one exists; never invent a task. Do not claim a fix without committed code and proof. Use supported inline thread replies for inline findings. For review-body or issue-comment findings, use supported conversation replies that quote or link the origin ID; do not use an inline-only endpoint.

Posting is narrowly authorized for scoped PR replies. Use target-specific `.env.local` `CODEINFO_PR_TOKEN` parsed as data, provided only as child `GH_TOKEN`; never print/evaluate/save/export it, interpolate into arguments, or place it in a remote URL. First use installed GitHub CLI when safely available; otherwise use a discovered installed skill/tool with supported remote API instructions. Verify the exact host, repository, identity, and permissions. Never guess. If unavailable, preserve the missing reply as unavailable and continue other safe targets.

Make replies idempotent with a marker keyed by source identity, disposition, and repair candidate, not batch. Inspect live replies before posting. Reuse an identical existing reply; a new meaningful proof/fix may update the agent's own reply or append one correction while preserving audit history. Failed or ambiguous publication is unavailable, never fabricated.

Assess each target's exact remote launched/reviewed head, later candidate heads, outstanding actual findings and reply coverage, changed fix-bearing HEAD needing a new review, unchanged unavailable actions, and late candidates that need another gates pass. Keep later administrative/checkpoint/documentation HEADs distinct from the exact head reviewers actually reviewed; never claim a newer head was reviewed. Preserve per-provider refusal/quota/failure and comparison limitations alongside usable sibling findings in the existing batch outcome/settlement, without requiring every provider to succeed or forcing the whole cycle incomplete solely for a terminal provider decline. Repeat only justified useful actions. Never request a new review for an unchanged candidate or retry unchanged quota/refusal/failure.
