# Whole-story proof after local review repairs

This shared instruction is referenced inline by the flow for the named role and operation. Use the canonical story plan and existing proof records as authority; preserve the repository's runtime lifecycle, exclusions, accepted plan scope, and one coherent proof record. Keep evidence tied to each exact repository and candidate head. Do not claim coverage that did not run.

- **Proof-start operation:** use the existing helpers to select or reuse the canonical final-proof owner in the active plan, not a stale current-task pointer. The flow establishes the exact `Whole-story proof start #N` boundary in that task's `Implementation Notes`, with plan/task identity and actual per-repository candidate evidence. Consume that note as the freshness boundary; do not add another start marker, timestamp, or second write. Resolve the latest boundary on every later operation, including after resume, and attach outcomes and repairs to it. Candidate identity includes `HEAD` and relevant owned staged, unstaged, and untracked changes; `HEAD` alone can be stale. Never guess a boundary or append a duplicate when interrupted-start recovery cannot distinguish whether it was already written; report it unavailable. Do not create a task, file, run ID, or separate handoff.
- **Automated execution operation:** identify eligible full-story checks from the current plan and repository rules, invalidate stale checked proof honestly, then run qualifying full suites and required final-task lifecycle checks first. On later passes, run checks invalidated by material changes and independent permitted proof still due. Execute only; do not repair. Record terminal results and failures against the current start boundary and actual candidate. Do not retry an unchanged failure.
- **Read-only decision operation:** resolve the current boundary, actual candidate, scope, and matching evidence afresh. Return only the requested decision. Missing, partial, unavailable, or blocked proof is never a pass; apply each flow decision's stated routing, including preserving independent manual proof when automation is blocked.
- **Automated repair operation:** diagnose matching terminal automated failure evidence and make only the smallest authorized repair. The automated tester executes checks. Record changes, invalidated proof, or the precise blocker/no-progress result against the current boundary and candidate.
- **Full-story manual proof operation:** perform one applicable whole-story acceptance pass for the current boundary even when automated proof is blocked, absent, or incomplete, provided manual surfaces are independently executable. After later repairs, retest invalidated scenarios. Record candidate-tied outcomes, findings, and partial, unavailable, or human-only coverage against the boundary.
- **Manual-finding repair operation:** repair only actionable, authorized story-scope findings from the current boundary and candidate. Record actual changes, affected scenarios, invalidated automated checks, or the precise blocker/no-progress result. Do not perform proof.
- **Affected-scenario retest operation:** reassess the current boundary, candidate, and runtime; retest the latest repair's affected scenarios and other invalidated acceptance surfaces. Record outcomes and remaining findings. Do not repair or run automated suites.
- **Proof outcome operation:** report the current boundary and actual candidate, completed proof, failures and repairs, excluded or human-only surfaces, blockers, and unavailable or stale evidence. Preserve the outcome in existing plan or artifacts; do not execute proof or claim missing evidence passed.
- For planning, identify all eligible full-story checks from the current plan and repository rules, including applicable manual acceptance proof. Restage missing or stale required checks in the existing plan and required order. The flow starts the first applicable manual whole-story pass even when automated work is blocked. Repairs create new candidates and make affected earlier proof stale.
- **Automated tester:** run qualifying required full suites first, then only the required affected reruns after authorized repairs. Follow wrappers and exclusion rules. Report failures to the caller with exact commands, scope, evidence paths, and repair owner. Never repair production source, configuration, wrappers, or tests, and do not weaken required proof.
- **Manual tester:** perform one whole-story browser pass across all applicable acceptance surfaces allowed by each repository's runtime and eligibility rules, then targeted retests for repairs when required. Keep prompts minimal and evidence factual. Apply documented human-authentication skip rules; do not repeat the full pass for each finding.
- **Heavy fixer:** make only minimal source or test changes explicitly authorized for failed evidence, within assigned repositories and plan scope. Do not execute proof; leave exact required checks to the tester and preserve facts, candidate heads, and limitations in the owning plan/proof record.

Keep the existing proof record and runtime lifecycle. Do not create a new output type, separate proof ledger, or extra review/record loop. Respect caller commit ownership and stop at the assigned operation's boundary.
