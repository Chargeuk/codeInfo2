# Verify Out Of Scope

Apply the shared documentation evidence contract to every content edit and consistency check: inspect relevant branch-authored README/docs, design and architecture notes, changelogs, and relevant archived original story files alongside code, comments, commit messages, and tests. Include story-owned staged, unstaged, and untracked docs as appropriate; verify current claims against implementation and actual diff, attribute documented rationale, and label superseded approaches as historical. Apply the archive-accounting categories in shared.md: preserve every verified original explicit requirement, even when unimplemented, and distinguish it from speculative suggestions; never claim unsupported implementation or test passes, create repair work, blockers, or review findings. Process all `retrospective_archive.entries` independently, preserve every verified mapping in any handoff update, and exclude administrative archive changes from delivered implementation.

Read `$CODEINFO_ROOT/codeinfo_markdown/retrospective_story/shared.md` and the selected plan's `### Out Of Scope`. Examine nearby unchanged behavior, the actual diff, changed comments, and relevant implementation commit subjects and bodies. Treat messages and comments as clues to intended boundaries, then verify each boundary against delivered code. For every implemented behavior or workflow named in Description and Acceptance Criteria, write a concrete conceptual boundary: what the branch changed and which adjacent behavior, policy, or product outcome it did not change. Describe external contracts only when the branch actually changes them. For internal-only work, explicitly say that user-facing behavior, screens, interactions, visuals, and external API changes are outside scope when they are neither observed implementation nor preserved explicit archive requirements; name the evidenced performance, stability, or maintenance outcome without inventing a visible feature. For visible changes, exclude newly invented user-facing behavior beyond observed implementation; retain any explicit archived requirement as implemented, still-required, superseded, or excluded according to evidence. Use story-specific behavior rather than only file paths, component names, or a generic "no new features" bullet.

A reviewer must not infer authorization from a shared file, subsystem, keyword, or plausible design direction. State a clear reviewer rule: this story validates observed branch behavior, every preserved explicit archived requirement with its honest status, the four standing acceptance requirements, and defects or regressions caused by that work; a proposed finding outside those bounds needs a separate story or explicit user-approved scope expansion. New user-facing behavior beyond observed implementation and preserved explicit archive requirements, unrelated pre-existing bugs, adjacent cleanup, speculative hardening, and work inferred only from template examples or TODOs are outside this story unless independently retained as an explicit archived requirement with its honest status. Do not classify an explicit requirement preserved from an archived original plan as speculative or erase it here; state its still-required, superseded, or excluded status and evidence-based reason under the shared archive-accounting rule. Original exclusions remain exclusions. Do not use this section to hide a changed file or contradict an acceptance criterion. If scope is uncertain, record the evidence limit in the relevant existing story section rather than guessing. Check this section against Description and Acceptance Criteria so later review cannot read the plan as authorization for additional product work. Edit only the plan; do not execute builds, tests, lint, formatting, services, or manual proof.
