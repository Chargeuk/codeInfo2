# Collect pinned PR review evidence

Follow `review_job_workspace_contract.md` and `$CODEINFO_ROOT/codeinfo_markdown/shared/review-artifact-handoff.md`. Use the scheduler-assigned `review_job` and `review_batch` paths; read `job.md`, every assigned input, immutable `batch-launch.md`, and all accumulated work evidence. Use the supplied target/review wave for exact repo, snapshot HEAD, and base. Do not require a target-local current-plan handoff. Do not select a sibling, change pinned Git/plan/implementation, adjudicate locally, repair findings, or run a local substitute review.

For every API/tool call, follow `prepare_pr_agent_review.md`'s secret-safe target-specific authentication procedure afresh; this step runs after the prepare step's child process environment has ended. Never rely on inherited/persisted tokens or conversation-only credential context. Collection is read-only: do not request reviews or otherwise mutate GitHub. Before and after fetching, recheck the exact PR candidate, live head SHA, intended base branch, actual base SHA, and immutable comparison-base SHA. A base SHA that advanced on the same intended base branch does not by itself invalidate the PR; inspect the actual diff and correlate comment applicability with the pinned comparison and story scope. If the candidate head moves during collection, retain fetched evidence with its actual provenance and mark coverage of the pinned candidate accordingly; do not claim a newer head was reviewed. Mark comparison coverage unavailable only when the diff or comment applicability genuinely cannot be established, not merely because the base branch advanced.

Fetch every page from all three PR feedback channels: inline review comments and thread replies; review bodies; and PR issue/conversation comments. Preserve useful raw evidence secret-free under assigned `work/`, including author, URL, numeric/node IDs where available, thread/reply IDs, body, timestamp, source channel, original/review commit, and exact pinned candidate/request linkage (or `Unknown`). If a channel cannot be fully fetched, record why and mark collection partial. Do not silently omit pages or evidence.

Produce ordinary self-describing common findings under assigned `output/`. For each actual finding include severity, repository, path and line when evidenced, concrete evidence, expected behavior, requested direction, source identity/URL/channel, and provenance/head applicability. Preserve sibling and partial findings. Separate actual findings from terminal no-findings acknowledgement, refusal/quota/failure, control chatter, stale feedback, and unattributed evidence. Do not promote unknown provenance to current-head coverage. Stale feedback can remain unresolved evidence with applicability explicitly checked; it never establishes current-head cleanliness. Existing review gates own scope, authorization, materiality, and disposition.

For each requested reviewer, state exact roster, launch and acknowledgement evidence, terminal state, exact remote head reviewed, actual base SHA, immutable comparison-base SHA, and missing comparison coverage. A terminal no-findings acknowledgement is distinct from findings. A terminal refusal, quota, or failure makes only that reviewer's coverage unsuccessful/unavailable; preserve it alongside valid sibling findings and continue ordinary shared best-effort batch processing and settlement. Do not claim every reviewer succeeded or demand an entire-flow-incomplete outcome solely for a provider decline. Include all three channel fetch statuses. State exact reviewed head separately from any later current administrative, documentation, or checkpoint head; never imply that an unreviewed later head was reviewed. Reopen and enumerate actual files under assigned `output/`, then report their factual paths and whether the handoff is complete, partial, or unavailable. If no channel evidence is recoverable, say so honestly; do not invent a successful review.
