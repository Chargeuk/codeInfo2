# Verify Acceptance Criteria

Apply the shared documentation evidence contract to every content edit and consistency check: inspect relevant branch-authored README/docs, design and architecture notes, changelogs, and relevant archived original story files alongside code, comments, commit messages, and tests. Include story-owned staged, unstaged, and untracked docs as appropriate; verify current claims against implementation and actual diff, attribute documented rationale, and label superseded approaches as historical. Apply the archive-accounting categories in shared.md: preserve every verified original explicit requirement, even when unimplemented, and distinguish it from speculative suggestions; never claim unsupported implementation or test passes, create repair work, blockers, or review findings. Process all `retrospective_archive.entries` independently, preserve every verified mapping in any handoff update, and exclude administrative archive changes from delivered implementation.

Read `$CODEINFO_ROOT/codeinfo_markdown/retrospective_story/shared.md` and the selected plan's `### Acceptance Criteria`. Check each delivered behavior in the supported merge-base-to-initial-HEAD story delta per shared.md when available, changed tests, current implementation, newly added or modified comments, and relevant implementation commit subjects and bodies. Use comments and messages to identify intended behavior and rationale, then verify every criterion against the delivered code. Write concise acceptance bullets for behavior actually delivered, including evidenced error and boundary behavior, and preserve every explicit archived acceptance requirement with its implemented / still-required / superseded / future-excluded status; do not claim an unimplemented requirement passed. These criteria verify delivered branch behavior and preserve explicit archive requirements as validation criteria without claiming they passed; they do not add speculative features, interface changes, or unrelated cleanup. Do not claim a test passed because its source exists. Edit only the plan.

Always include acceptance criteria, in wording appropriate to the story, that require all four of these outcomes:

- Newly added code is used: no unused variables, parameters, functions, statements, or redundant lines remain.
- Substantive new or modified code has accurate high-level comments explaining both what it does and why the change was made.
- Changes do not leave variables or parameters in previously existing code unused after their former use was removed or replaced.
- Appropriate automated tests cover the new behavior already delivered, including relevant error and boundary cases. This is a criterion for later validation; this documentation flow does not judge coverage, write tests, or execute them.

State explicitly that no newly invented user-facing behavior, interface, visual, or API changes are required beyond observed implementation and preserved explicit archive requirements. Keep any requirement categorized as still-required visible as a validation requirement, without claiming delivery. When the work is internal only, describe its observed performance, stability, or maintenance outcome without implying a new screen, interaction, or external contract. Existing visible behavior and interfaces remain as evidenced by the branch. Use changed code, callers, and test sources to describe implemented behavior; preserve archived explicit requirements separately with their evidence-based status. Do not assess whether the code or test coverage passes these criteria, list suspected defects, add blockers to Implementation notes, or expand the final task with perceived missing work. Leave final validation to the later execution of the open final task. Do not build, run tests, lint, format, start services, or perform manual testing.
