# Parallel automated candidate proof

Use the scheduler-assigned parallel batch context for this child’s immutable snapshot and working repository. The parent binds its opt-in directly to this child, defaulting an omitted flag to false. Run proof only if the assigned `parallel_automated_validation` is exactly boolean `true`; false means deliberately not applicable, and any other value means unavailable. Do not infer opt-in from a plan or another invocation.

Use only the assigned snapshot, not a mutable latest pointer. Identify each target by its exact root, branch and full pinned HEAD. Review is running concurrently; do not edit source, tests, plan, Git state or reviewer artifacts, and do not start manual proof. Before running a check and again after it, establish that the affected worktree still represents the pinned candidate, including relevant staged, unstaged and untracked source/test changes and other active writers. If equivalence or exclusive use of a necessary test resource cannot be established, report that check unavailable and continue independent safe checks. Never claim proof for a changed or dirty candidate as proof of the committed snapshot.

For a same-head gates-only PR pass, reuse attributable successful applicable validation for the identical candidate when the existing PR cycle evidence positively identifies that pass; do not rerun it. Record the source wave and evidence in this wave’s result. If an apparent same-head pass or its applicable evidence cannot be established, report the limitation rather than guessing. For an ordinary enabled pass, execute the applicable repository-required builds and full automated checks using its wrapper and heartbeat rules; honor explicit task and story exclusions and document their exact scope. For this repository full-suite means exactly one applicable `test:summary:all:parallel` or `test:summary:all:stress` per unchanged candidate, and required build wrappers as specified by current repository guidance. No manual tests. Capture exact commands, terminal pass/fail/skip or unavailable results, logs, affected target and candidate, and actionable failure evidence. A failure is not automatically a review finding. Do not repair or repeat an unchanged failure.

Write a structured JSON result at the plan host under `codeInfoTmp/reviews/<exact review_wave_id>-parallel-automated.json`, using the exact snapshot ID and an atomic write; never choose another wave or touch scheduler-owned launch/job files. Include `review_wave_id`, `review_cycle_id`, `targets_sha256`, each target root/branch/head, `status` (completed, partial, unavailable, or not_applicable), opt-in evidence, commands and results, failures with evidence paths, exclusions, and limitations. If writing is unavailable, report that explicitly in the terminal result. Verify the saved result belongs to this snapshot. Do not invent success or treat unavailable coverage as clean.
