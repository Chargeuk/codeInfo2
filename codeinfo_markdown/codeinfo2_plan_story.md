# Discuss a story and develop a local plan

Help the user choose, discuss, and document one story as a local planning file in the selected target repository. The local file is the working story. Use this command to plan only; stop before implementation.

Start by identifying the selected repository root from the supplied working folder and available local Git/source evidence. Read its root `AGENTS.md` if present, plus relevant documented planning guidance and available skills. Do not invent paths or assume a repository. A remote repository or Jira access is not required: when the local target or supplied plan path is safely known, unavailable Git, remote, or Jira access must not prevent useful discussion and local planning.

## Choose a story

If the user supplied a story, idea, or local planning-file path, begin with that information without requiring a picker or complete clarity. Draft provisionally from the known goal, label assumptions and open questions, and ask only focused follow-ups needed to improve it. If there is no meaningful story subject yet, ask what they want to achieve; otherwise offer useful choices such as browsing available Jira Bugs or Stories, finding a local story/plan, or starting a new local story. Do not infer a ticket from an unrelated active handoff or select an existing local plan from workflow state.

Use the selected repository's documented and configured tools or skills to discover whether Jira can be used. Do not assume a project, board, site, account, path, endpoint, identity, or credential. Jira listing and reading are optional conveniences: if Jira is absent, inaccessible, unconfigured, permission-limited, or fails, explain the limitation briefly and continue local planning from the user's input. Make reasonable best-effort reads using the supported tool's normal bounded pagination; do not add helpers, schemas, receipts, gates, or a repository-wide audit. Use `code_info` first for consequential questions about the selected repository, then verify decision-relevant source and configuration directly. If that tool is unavailable, say so when relevant and continue from trustworthy evidence.

Keep initial Jira browsing and story discussion read-only. A Jira write is allowed only as a concise comment on the issue the user selected, recording genuinely agreed planning decisions and the local plan path when useful. The user's selection and agreement to document those decisions authorize the comment independently of local-save success; report the save status truthfully and do not present proposals as agreements. Never edit or resend the issue description, overview, acceptance criteria, custom fields, or other fields; never change status or assignee; never create or update an issue or subtask. Use only a repository-supported safe comment method and a verified identity. If identity, permission, or outcome is unclear, skip or report the comment limitation and continue local work. Before retrying an uncertain comment, read back recent comments and check whether it already succeeded; do not blindly duplicate it. Never claim an unsaved change was persisted. Report Jira source and comment outcomes separately as confirmed, failed, unavailable, or uncertain.

## Develop the local plan

Create or develop a candidate local plan from the known story goal when the subject is meaningful; unanswered scope questions may remain clearly recorded in the draft. Save when the target path is safely established and the story is sufficiently identified, without asking for redundant filename or location approval when conventions make the choice clear. Check the selected repository's documented planning location and relevant no-task story template when present, then follow its established filename and story-content conventions. For example, when verified in that repository, prefer a seven-digit identifier and descriptive title under `planning/`. Otherwise use a descriptive, unique filename in the documented planning location, with a sensible repository-local fallback if none is documented. Preserve existing paths, layout, identifiers, history, and developed content. Do not overwrite a same-title file, renumber work, or choose an existing file unless the user explicitly identifies it as the candidate. Do not copy template workflow actions that exceed this command's boundaries, including branch creation, story selection, task creation, or test execution. Do not read or update `current-plan.json` or other workflow state to choose or select the plan.

If the target path, permissions, filesystem, or required Markdown writer cannot be safely established or used, skip only the save. If `AGENTS.md`, a template, or other guidance is unavailable or unreadable, skip only that read and continue using known conventions and defaults; do not block saving when the path and writer are safe. Do not guess paths, overwrite files, or bypass role permissions. Preserve valid partial results, continue safe useful planning and conversation, and show the best available provisional draft inline labeled unsaved or partial, stating exactly what could not be read, saved, or posted. Missing tools, Jira, Git, or remote access limits only the affected operation, not other useful local work. Never claim an unsaved draft was saved.

For a Jira-backed plan, faithfully carry over the readable issue overview, acceptance criteria, source key, and link. Preserve the distinction between agreed requirements, open questions, and unagreed proposals. Retain Jira provenance even as the local plan is expanded. If Jira cannot be read, draft from the user's material and state material unknowns honestly; do not invent ticket facts.

Use the local plan to capture the story development, normally in the repository's existing layout. For a new plan, default to Overview, Acceptance criteria, Out of scope, and Best practices unless the target repository's template uses a semantically equivalent layout. Preserve an existing plan's useful layout and developed content. Capture agreed scope, relevant best practices, and material justified deviations in the plan. Verify claims about current repository or source behavior against available source and guidance. Keep user- or agent-proposed implementation ideas, suggestions, and questions labeled as unverified proposals, separate from confirmed facts and agreed requirements. Record a proposal as an agreed requirement when the user adopts it; do not treat it as an agreed acceptance criterion without that agreement. Where target guidance or the story makes explanatory code comments useful, describe what they should explain and why; do not require low-value comments or contradict target guidance.

Make acceptance criteria measurable and story-scoped, with relevant planned proof only. Include both cleanup outcomes: no unused code introduced by the story remains, and code made unused specifically by the story is removed. Keep both scoped to this story; do not authorize unrelated cleanup. Favor KISS, minimal changes, established helpers and patterns, consistency with comparable flows, and contextual errors. Where relevant, plan best-effort handling of independent failures, useful failure context, preservation of valid results, and responsive behavior. Do not add speculative gates, prerequisites, unrelated product fixes, or refactors.

Describe only proof relevant to the agreed story and the target repository's documented testing requirements. Do not require Kadshow VR, Patreon, Jest, Cucumber, new tests, or unrelated checklists by default. Do not silently grant blanket authority to repair brittle tests: include such authority only when the user or target repository's applicable documentation explicitly allows it. Respect explicit user scope and testing restrictions over defaults.

The user may adopt a suggested implementation idea during discussion; record that decision as an agreed requirement. A later planner may adopt, adapt, or reject remaining proposals, with a brief reason for material departures. Unadopted proposals stay labeled and never override agreed acceptance criteria or scope. This file is for story planning; do not turn it into detailed implementation tasking.

## Boundaries and response

Do not change story-selection/current-plan/current-task/review state or other workflow files. Do not create or switch branches, commit, push, open a pull request, implement the story, create implementation tasks or subtasks, or execute tests. Do not import `codeinfo2_implement_story` workflow requirements wholesale; this command has the narrower contract above.

Continue the discussion as needed to round out the plan, then stop before implementation. Leave current story selection and handoffs untouched. In the final response, give the candidate plan path, a concise summary of agreed scope and open questions, and separate Jira source/comment status. Do not claim a Jira comment or local save unless it is confirmed.
