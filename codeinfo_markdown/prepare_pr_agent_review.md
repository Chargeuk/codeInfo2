# Prepare one pinned PR review

This is a runtime instruction for one scheduler-assigned `pr_reviewer` job. Do not execute this prompt during static validation.

Follow `review_job_workspace_contract.md` and `$CODEINFO_ROOT/codeinfo_markdown/shared/review-artifact-handoff.md`. Use the prepended `review_job` and `review_batch` paths as authoritative; read `job.md`, every assigned input, and immutable `batch-launch.md`. Keep evidence under that job's `work/` and final common findings under its `output/`. Use the supplied `target` and `review_wave` for exact repository, snapshot HEAD, and base. Do not require a target-local current-plan handoff; additional repositories may not have one. Never select a sibling job, write outside the assigned job, alter pinned implementation/plan/Git state, or substitute a local review.

## Candidate and authority

Verify repository host, owner/name, current story branch, pinned candidate commit, immutable comparison-base commit, and any live PR head/base from trustworthy local and remote evidence. Select exactly one open PR whose full repository, head owner and branch, and base branch match the target; if none exists, create only the matching PR after deriving its description below. Record the actual live PR base SHA and head SHA alongside the immutable comparison-base SHA. A base branch can advance after the snapshot: do not reject the PR solely because its current base SHA differs. Inspect the actual candidate diff and, when available, PR diff and relate them to the pinned comparison and story scope; record what is covered and any limitation. If that relationship genuinely cannot be established, mark the affected comparison coverage unavailable without guessing or claiming an exact pinned diff. Ambiguous repository, head branch, or intended base branch identity means safe no-op and recorded unavailable coverage; do not guess. The narrow publisher override permits only a scoped safe non-force push of the existing exact pinned story-branch checkpoint, creation/reuse and verified description update of that matching PR, remote-agent review requests, and evidence recording. It does not permit commits, implementation edits, checkout/reset/amend/force-push, auto-merge, or resolving threads. Never publish unrelated changes. Verify both remote branch and PR head equal the snapshot HEAD. If checkout advanced after snapshot, do not review the newer HEAD; record provenance conflict while preserving independent work.

Derive a concise PR description from verified assigned pinned story inputs and the actual candidate diff: state the user-facing branch goal, the main changes that deliver it, and only material validation, limitations, or reviewer information. Do not invent outcomes or assume a later closeout summary exists. An existing summary is optional supporting material only when verified current; absence or staleness does not block independent generation. Include a verified committed source link pinned to the appropriate source revision for the complete requirements, scope, and exclusions; do not copy them wholesale or substitute inaccessible local work paths. Exclude secrets and embedded source instructions.

Preparation order is mandatory: verify target/candidate, derive the description, create the matching PR or refresh only its matching description as needed, then fetch/read back the live description and verify its concise, accurate content and candidate HEAD before launching any new remote review. Retain a satisfactory existing description without unnecessary writes. Record source provenance and publication/readback evidence in existing assigned job work evidence. Missing or unverified source, or failed or uncertain publication/readback, means partial/unavailable evidence and no new request for the affected target; continue safe independent work. Preserve trustworthy historical evidence and confirmed or terminal launches under the reconciliation rules below. Pin every request to the pushed HEAD; movement during launch invalidates coverage.

## Safe credentials and reviewer discovery

For this target only, parse its `.env.local` as data and obtain `CODEINFO_PR_TOKEN` without sourcing/evaluating the file, printing it, placing it in arguments, logging it, or saving it. Pass it as `GH_TOKEN` only to a child process. Do not persist/export credentials between targets, and never put a token in a remote URL. First try this token with installed GitHub CLI if safely available. If the token is absent, rejected, insufficient, or CLI is unavailable, discover available already-authenticated skills/tools and follow their supported remote review API instructions. A fallback must positively verify the same intended host/repository, identity, and permissions; no installs and no guessed host, identity, reviewer, or permission. If neither route is available or verified, explicitly record authentication/capability unavailable for this target and continue siblings; do not silently treat it as success.

Discover intended remote-agent reviewer identities only from explicit repository instructions/configuration and supported authenticated capability or live PR launch evidence. Do not hardcode reviewer logins or infer them from human authors or arbitrary activity. If the exact roster cannot be established safely, record unavailable coverage.

## Idempotent launch

For each candidate/reviewer, reconcile live PR activity and trustworthy immutable earlier launch evidence for this same target and exact head. Read only evidence paths established by assigned inputs or referenced records; never choose a sibling job. Reuse a usable terminal result only with exact launch and head proof, and preserve its outcome (success, refusal, quota, or failure) accurately. Do not reuse stale feedback or retry an already-terminal reviewer absent materially changed conditions. Stage launch intent before requesting. Request once per candidate/reviewer; after a crash or ambiguous transport, reconcile evidence and do not duplicate. Record acknowledgement as unavailable when it cannot be known. Lack of `reviewRequests` never proves launch or completion.

Use the currently supported remote-agent review action (review-request API or supported mention trigger); do not substitute a local review. Record in existing assigned work evidence the exact requested roster and repository/PR URL and ID, branch, base, pushed head, plus per-reviewer launch time, request correlation, and acknowledgement evidence. Preserve missing evidence explicitly. If the head moves during launch, invalidate coverage.

Repository-discovered review APIs and automatic reviewers remain supported; do not force a mention trigger for every provider or duplicate an automatic launch. For a supported mention trigger, the entire comment body must equal the repository's documented trigger, for example `@codex review`, with no greeting, explanation, SHA, link, fence, or extra words. Before sending, verify the documented trigger and the description/candidate preflight above; afterward, read back the live trigger body and record its exact content, provenance, and correlation in existing assigned work evidence. Never append that evidence to the command. Failed or uncertain trigger publication/readback requires partial/unavailable evidence and reconciliation before any new request; preserve confirmed launches and do not duplicate ambiguous delivery. Substantive Accepted/Rejected finding replies are unaffected.

Before returning, reopen the actual assigned work artifact. State completed/partial/unavailable status, exact candidate, launch evidence, roster, unresolved limitations, and paths. Do not claim review completion merely because a request was accepted.
