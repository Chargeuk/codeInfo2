# Retrospective story contract

This flow documents implementation that already exists. It is not a code review or a test-adequacy review. Every agent step is documentation-only: read Git, source, branch-authored documentation, comments, commit messages, existing test files, logs, and read-only status helpers; edit only the new story plan and its handoff, apart from the explicitly requested first-step archive and ignored receipt, branch creation, branch pushes, and plan-only commit. Never build, execute tests, run lint or formatting tools, start services, perform manual testing, capture screenshots, or modify implementation or test code. The native reingest steps are part of the flow and may run as configured. Read the target repository's `AGENTS.md` and `codeinfo_markdown/repository_information.md` when present. Use `code_info` first for repository facts, then inspect Git and source files directly. Treat indexed content as navigation help; Git and current disk contents establish the actual work.

The first step archives every verified top-level numbered story matching the fresh current branch's numeric story ID, in deterministic filename order before working reingest. Several matching files are confirmed scope, not ambiguity. Discover current sources afresh on every invocation; a prior receipt never suppresses a present replacement source. Allocate `planning/one-shot/one-shot-<original-stem>.md`, then `-1.md`, `-2.md`, and so on before the extension using exclusive creation; occupied names and allocation races advance the suffix rather than skip the source. Existing archives remain untouched. No matching source is a normal no-op; unknown branch identities and unsafe paths are safe no-ops. Per-file errors are nonfatal and do not stop remaining verified sources or the flow.

Recover outcomes independently from the ignored `codeInfoStatus/flow-state/retrospective-archive.json` receipt and repository evidence, never a previous agent report. The receipt's `entries` list contains each source path, allocated archive path, content hash, status, and reason. Independently verify every mapping: a top-level numbered source matching the recorded branch's numeric ID, a regular archive file under `planning/one-shot/`, the exact `one-shot-<original-stem>.md` or positive integer suffix relationship, and bytes matching `content_sha256`. A present source does not invalidate an earlier mapping: it may be a replacement that must also be archived. This preserves evidence of original dirty or untracked content after source-path reuse. Keep all verified prior mappings alongside fresh outcomes, including earlier pending archives when HEAD advanced on the same numeric story; a no-source repeat recovers them without moving archives. If a move created a verified archive but failed to delete its source, retain that mapping and its error honestly; retry the still-present source on the next invocation.

Before layout copies the receipt, verify its fresh branch and initial HEAD against Git and validate its entries independently. Copy it as `retrospective_archive` in the new current-plan handoff; preserve it through branch publication, renumbering, and every later handoff update. Later agents process all `retrospective_archive.entries` independently and retain every verified archive mapping even if layout selected a different branch number. Missing, malformed, stale, conflicting, or unverifiable entries are factual evidence limitations: salvage verified mappings, inspect Git and archive paths for trustworthy facts, omit unsafe staging, and continue safe plan work. Do not guess destinations from a base filename or assume only one archive. Never repoint the active handoff to a one-shot filename, which lacks the required numbered-plan prefix. Number allocation continues to scan only top-level `planning/*.md`; archiving all matching plans frees the number unless another top-level plan or same-namespace branch collides.

Exclude generated new plans, all verified archive destinations, and each administrative source deletion from delivered implementation inventory and base-to-HEAD or dirty-work comparisons. Do not let the archive alter the supported comparison base or manufacture delivered behavior. If the new plan reuses an old source path, that path is the new administrative plan, not additional implementation. Read relevant archived original story files as contextual documentation and compare their claims against actual implementation; archive relocation itself is never a completed implementation task. The final plan-only commit includes every independently verified archive destination, relevant tracked source deletions when still deleted, and the selected new plan, deduplicating repeated or reused paths. Per-file errors remain visible; an undeleted source is never represented as a successful deletion. The ignored receipt is never committed.

Throughout layout, section writing, tasking, checking, repair, audit, and commit preparation, inspect relevant branch-authored documentation alongside code, comments, commit messages, and tests: README files, docs, design and architecture notes, changelogs, and the archived original story where relevant. Inspect committed diffs and story-owned staged, unstaged, and untracked documentation as appropriate. Current behavior claims must agree with current implementation and the actual diff. Use relevant earlier commits and code for historical evolution; clearly label abandoned or superseded approaches as historical, never current delivered behavior. Attribute documented rationale to its documentation and verify consistency with code; code does not prove motivation. Authored documentation and tests do not prove execution or test passes. Original-plan proposals, template text, and unsupported documentation claims remain unverified or are omitted from delivered scope; they never create extra features or tasks. Documentation/code disagreements are factual evidence limits, not blockers or code-review findings. All content edits follow this documentation evidence contract.

The initial layout step creates this flow's plan and replaces any older current-plan handoff; it must discover branch evidence independently. The immediately following branch-publication step rereads that handoff, rechecks live same-namespace branch numbers, and attempts to push the selected branch before section writing. A push failure is an evidence limitation, not a flow stop. On every later step, read `codeInfoStatus/flow-state/current-plan.json` to identify the exact `plan_path`, `comparison_base_commit` when established, `initial_head_commit`, and additional repository scope. Confirm the handoff points to an existing retrospective plan for the current branch before editing it; an old or unverified handoff is not authority to edit another story. Reopen the selected plan from disk and recover needed facts from the plan, Git, source, and repository instructions rather than a prior agent's conversation or step report. Do not select another plan or invent a missing comparison base. Compare a supported base to the initial HEAD and separately inspect staged, unstaged, and untracked work; exclude the newly generated plan from implementation evidence. If the base is ambiguous or unavailable, preserve `comparison_base_commit: null`, document the candidate ranges and their differences in `## Implementation Ideas` and relevant task Implementation notes, and use only changes directly supported by Git and current source. If HEAD or relevant source changes drift during the flow, refresh the evidence and explain the changed snapshot in the plan. Continue with the best supported story; when the plan identity cannot be verified, make plan edits a safe no-op and report the limitation.

Inspect dirty work to identify its relationship to the story. Document story-owned staged, unstaged, or untracked implementation as local-only evidence with exact paths and an explicit warning that a plan-only push will not publish those changes. A task may describe implemented work on disk, but must not claim an implementation commit or remote availability without proof. Keep unrelated dirty files untouched. Do not let imperfect evidence prevent tasking, audit, or a safe plan-only commit attempt; preserve material limitations in the relevant existing story section and `#### Implementation notes`.

Read only the bounded sections of a large plan using `$CODEINFO_ROOT/scripts/plan_sections.py` or focused `rg` and `sed` reads. Do not write secrets or machine-specific paths outside the plan's `Additional Repositories` entries. Keep the plan's user-facing scope tied to observed branch changes and explicit user instructions; do not invent intent, outcomes, test passes, or commits. A source change is evidence of implementation, not evidence that an automated or manual test passed.

For each story-owned change, inspect the changed code and tests, newly added or modified comments in the diff and current source, and the subject and body of relevant implementation commits. Use bounded Git history: list candidate commit SHAs and subjects first, then read the bodies of relevant commits and their diffs. Comments and commit messages can explain intended behavior, motivation, and task boundaries, but are claims to verify against current code, tests, and the actual diff. When they disagree, document the discrepancy rather than repeating stale intent as delivered behavior. Do not treat a commit message, a comment, or an authored test as proof that a test ran or passed.

This plan is a retrospective record, not authorization for additional product work. Its top-level `### Description`, `### Acceptance Criteria`, and `### Out Of Scope` are the scope contract that later tasking and review agents read. State explicitly in those sections that later reviewers should verify observed branch behavior, appropriate automated test coverage for delivered behavior, the three user-required code-quality criteria, and story-caused defects or regressions. This flow does not perform that review. Do not authorize any further user-facing behavior or interface change beyond the diff; for internal-only changes, describe only the evidenced performance, stability, or maintenance outcome and preserve existing visible contracts. Reviewers must not turn nearby issues, TODOs, template examples, preferred designs, or uncertain evidence into new features or unrelated repair tasks. Omit the Questions section from the generated story even when it appears in a source template; do not create or consult it at any step. Put material limits on identifying or attributing implemented work in the relevant existing story section or task Implementation notes. State acceptance requirements without judging whether current code or tests satisfy them. Do not add `- **BLOCKER**` lines, suspected missing-work lists, or code-review findings to any Implementation notes. A read-only status helper may report open work; that status is not an instruction to add blocker notes. Do not turn perceived code or test gaps into new tasks or final-task work. Evidence limits are not future implementation requests. A scope expansion needs an explicit user instruction and an updated story contract.

The templates are layout references only: exclude prospective planning instructions, the Questions section, and generic implementation-blocker guidance from this retrospective story. This flow's explicit no-blocker rule overrides blocker advice in `plan_format.md` and the shared final-task contract. The planning template lookup is: current working repository's `planning/plan_format_no_tasks.md`, then `codeInfo2` through `code_info`, then another indexed repository. The task template follows the same order for `planning/plan_format.md`. If no template can be found, use the headings established by the current repository's existing plans and report the fallback.

The final task is deliberately open. Follow `$CODEINFO_ROOT/codeinfo_markdown/shared/final-task-creation.md` for its shape and repository-supported commands. Document its future build, suite, lint, formatting, and manual checks without executing or checking them off in this flow. Earlier implementation tasks may be `__done__` when their work is demonstrated by Git and source evidence. Mark an earlier testing checkbox complete only with evidence of that exact test execution; otherwise leave historical test execution unstated or explicitly unverified and rely on the open final task for future full validation. The final task starts open with unchecked checks and no blocker lines in Implementation notes.
